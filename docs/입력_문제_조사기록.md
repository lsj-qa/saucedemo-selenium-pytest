# 조사 기록 — 특정 환경에서 키 입력이 화면에 도달하지 않는 문제

원인을 특정하지 못한 채 우회 수단을 쓰고 있습니다.
**어디까지 확인했고 왜 이렇게 처리했는지**를 남겨, 다시 볼 때 같은 길을 되밟지 않도록 합니다.

---

## 1. 증상

주문 정보 입력 화면(`checkout-step-one.html`)에서 세 칸(`first-name`, `last-name`, `postal-code`)에
**타이핑이 전혀 반영되지 않습니다.** 예외는 발생하지 않고 값만 비어 있습니다.

처음에는 "필수값 누락" 으로 뒤늦게 드러났습니다.

```
base.send_keys(CheckoutStepOne.first_name, "Sujin")   ← 입력했는데
AssertionError: 예상과 다른 메시지: Error: First Name is required   ← 비어 있다고 나옴
```

## 2. 재현 조건

| 운영체제 | 브라우저 | 실행 위치 | 결과 |
|---|---|---|---|
| Windows | Chrome | 로컬 | **정상** — 화면 유무와 무관 |
| Windows | Edge | GitHub Actions | **정상** |
| Linux | Chrome | GitHub Actions | **항상 실패** — 간헐적이 아니라 100% |
| Linux | Edge | — | 미확인 |

**운영체제로 갈립니다.** 브라우저를 Edge 로 바꿔 Windows 에서 돌렸을 때는 정상이었고,
리눅스에서만 재현됩니다. 크로스 브라우저 매트릭스를 구성하면서 확인된 사실입니다.

같은 실행 안에서도 화면마다 다릅니다.

| 화면 | 타이핑 |
|---|---|
| 로그인 (`/`) | **정상** |
| 주문 정보 (`checkout-step-one.html`) | **실패** |

로그인 화면 입력이 정상이므로 "이 환경은 키 입력이 안 된다" 는 설명은 성립하지 않습니다.

---

## 3. 배제한 가설

순서대로 하나씩 확인해 제외했습니다.

### ① 화면이 다 그려지기 전에 입력해서

**아님.** 실패 시점의 화면과 HTML 을 저장해 확인했습니다.
화면이 완전히 그려져 있고, 칸에 커서까지 들어가 있습니다.

`document.readyState` 가 `complete` 가 될 때까지 기다린 뒤 입력하도록 바꿔도 동일했습니다.

### ② 창이 '가려진 상태' 로 판정되어 키가 전달되지 않아서

**아님.** 해당 판정을 하지 않도록 브라우저 옵션을 추가했으나 변화 없음.

```
--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding
--disable-features=CalculateNativeWinOcclusion
```

### ③ 화면 없이 실행하기 때문에

**아님.** 가상 화면(xvfb) 위에 창을 실제로 띄우고 같은 테스트를 돌렸으나 동일하게 실패.
이 비교 실행은 `input-method-check` 작업으로 남겨 두었습니다.

### ④ 문서가 키보드 입력을 받는 상태가 아니라서

**아님.** 실패 시점에 칸의 상태를 직접 조회했습니다.

```
{'doc_has_focus': True,      ← 문서가 키보드 입력을 받는 상태
 'focused': True,            ← 그 칸에 포커스 있음
 'active_id': 'first-name',  ← 포커스 위치도 정확
 'on_top': 'first-name',     ← 덮고 있는 요소 없음
 'disabled': False,
 'readonly': False,
 'size': [380, 39]}
```

같은 화면에서 **마우스 클릭은 정상 동작**합니다. 버튼 클릭으로 화면 전환이 이루어집니다.

### ⑤ 페이지가 스스로 이동한 뒤라 키보드 연결이 새 화면에 붙지 않아서

**아님.** 로그인 화면은 자동화 도구가 직접 연 페이지라 되고,
주문 화면은 버튼 클릭으로 이동한 결과라 안 되는 것으로 보였습니다.

그래서 주문 화면을 **자동화 도구가 직접 다시 열고** 입력해 봤으나 동일하게 실패했습니다.
이동 방식이 아니라 **화면 자체**의 문제입니다.

---

## 4. 측정 결과

가설을 세우는 대신, 타이핑할 때 칸에서 실제로 발생하는 이벤트를 수집했습니다.

```javascript
element.addEventListener('keydown',     ...)
element.addEventListener('beforeinput', ...)
element.addEventListener('input',       ...)
element.addEventListener('change',      ...)
```

결과는 **`이벤트 없음`** 입니다. `keydown` 조차 발생하지 않습니다.
요소가 교체된 것도 아닙니다(표식을 남겨 확인).

세 가지 서로 다른 입력 경로를 모두 시도했으나 전부 동일합니다.

| 방식 | 결과 |
|---|---|
| 칸을 눌러 포커스 후 입력 | 값 `''`, 이벤트 없음 |
| 마우스·키보드 동작을 조합해 입력 | 값 `''` |
| 화면을 직접 다시 연 뒤 입력 | 값 `''`, 이벤트 없음 |

**정리하면** — 칸은 정상이고, 포커스도 정상이고, 마우스는 전달되는데,
**키 입력만 화면에 도달하지 않습니다.**

---

## 5. 조치

원인을 특정하지 못했으므로, **우회하되 우회한 사실이 드러나도록** 했습니다.

1. 실제 키 입력을 두 가지 경로로 먼저 시도합니다.
2. 모두 실패하면 값을 직접 넣고 입력 이벤트를 발생시킵니다.
3. 그때 **로그에 남깁니다.**

```
[실제 키 입력이 전달되지 않음 → 값 직접 입력] ('id', 'first-name')
[입력 방식 전환] ('id', 'first-name') → 3회차 '값 직접 입력' 로 성공
  경과: [...]
  칸 상태: {...}
```

**우회를 조용히 넣지 않은 이유** — 통과했더라도 실제 키 입력은 실패한 상태입니다.
그 사실이 감춰지면 "전부 통과" 라는 결과가 실제보다 좋아 보이게 됩니다.

`input-method-check` 작업은 이 비교를 계속 남겨두기 위한 것으로,
어떤 방식이 통했는지를 매 실행마다 기록합니다.

---

## 6. 남은 의문

다시 본다면 여기부터 보겠습니다.

- **왜 화면마다 다른가** — 같은 세션, 같은 브라우저에서 로그인 화면은 되고 주문 화면은 안 됩니다.
  두 화면의 입력 칸은 속성이 거의 같습니다. 차이는 주문 화면에만 상단 메뉴 영역이 있다는 점입니다.
- **왜 운영체제마다 다른가** — 페이지의 스크립트가 원인이라면 Windows 에서도 재현되어야 합니다.
  재현되지 않으므로, 사이트 쪽이 아니라 **리눅스에서의 키 입력 전달 방식**에 가깝습니다.
- 확인해 볼 것 — 리눅스에 Edge 를 설치해 같은 현상이 나는지(브라우저 문제인지 운영체제 문제인지 분리),
  문서 전체(capture 단계)에 키 입력을 가로채는 처리가 있는지,
  드라이버 버전 조합을 바꾸면 달라지는지

## 7. 판단

**이 저장소의 목적에 비추어 조사를 여기서 멈췄습니다.**

대상이 데모 사이트이고, **리눅스 실행 환경에서만** 나타나는 현상입니다.
Windows 에서는 두 브라우저 모두 실제 키 입력으로 정상 통과하므로,
사이트의 결함이라고 보기 어렵습니다.

더 파고들 수는 있지만, 얻는 것에 비해 시간이 많이 듭니다.

다만 **덮어두지는 않았습니다.** 우회했다는 사실이 실행할 때마다 로그에 남고,
어디까지 확인했는지가 이 문서에 남아 있습니다.
