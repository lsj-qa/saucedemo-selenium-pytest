# 테스트 설계

이 문서는 **무엇을 자동화했는지**가 아니라 **왜 이렇게 골랐는지**를 남긴 것입니다.
케이스 목록은 코드를 보면 알 수 있지만, 선정과 제외의 근거는 코드에 남지 않습니다.

---

## 1. 대상과 전제

| 항목 | 내용 |
|---|---|
| 대상 | [saucedemo.com](https://www.saucedemo.com/) — 데모 커머스 사이트 |
| 범위 | 로그인 → 상품 조회 → 장바구니 → 주문 완료 |
| 계층 | UI (브라우저) |
| 환경 | Chrome(Linux) · Edge(Windows), 데스크톱 해상도 1440×900 |
| 실행 | 로컬 / GitHub Actions (리눅스, 화면 없이) |

**전제** — 이 사이트는 서버 상태가 없고 계정이 고정되어 있습니다.
실제 서비스라면 테스트 데이터 준비·정리가 설계의 큰 축이 되지만, 여기서는 해당하지 않습니다.
대신 **상태가 화면에만 남는 구조**(장바구니가 브라우저에 유지됨)라서
화면 전환·이탈 후 상태 유지를 확인하는 케이스에 비중을 뒀습니다.

---

## 2. 리스크 기반 우선순위

전 기능을 균등하게 덮지 않았습니다. **깨졌을 때의 영향**과 **깨질 가능성**으로 나눠
높은 쪽에 케이스를 더 배치했습니다.

| 기능 | 영향 | 가능성 | 등급 | 배치한 케이스 수 |
|---|---|---|---|---|
| 주문 완료 | 매출 직결. 실패 시 대체 수단 없음 | 단계가 많아 중간 이탈 여지 큼 | **최상** | 5 |
| 장바구니 | 주문 전 단계. 수량 오류는 금액 오류로 이어짐 | 상태를 화면이 들고 있어 유실 위험 | **상** | 5 |
| 로그인 | 막히면 전체 이용 불가 | 조건 분기가 많음 | **상** | 7 |
| 상품 목록·정렬 | 조회 기능. 틀려도 거래에 직접 영향 없음 | 정렬은 값 비교라 결함이 드러나기 쉬움 | 중 | 6 |
| 푸터·외부 링크 | 없음 | — | 하 | 0 |

**로그인에 7건을 둔 이유** — 케이스 수가 아니라 **분기 수**를 따랐습니다.
차단 조건이 6가지(잠긴 계정, 비밀번호 불일치, 없는 계정, 아이디 미입력, 비밀번호 미입력, 둘 다 미입력)이고,
각각 **다른 사유**가 안내되어야 합니다.

**푸터를 뺀 이유** — 깨져도 서비스 이용에 영향이 없습니다.
자동화는 유지비가 드는 자산이라, 회수되지 않을 곳에는 만들지 않았습니다.

## 3. 케이스 선정 원칙

정상 동작 확인만으로는 결함이 잘 드러나지 않습니다.
다음 다섯 가지 관점을 각 기능에 적용해 케이스를 뽑았습니다.

| 관점 | 무엇을 노리는가 | 해당 케이스 |
|---|---|---|
| **되돌리는 동작** | 취소·삭제 시 데이터가 함께 사라지는 결함 | `test_checkout_cancel_keeps_cart`, `test_remove_from_cart` |
| **반복 조작** | 상태가 누적되어 어긋나는 결함 | `test_add_remove_repeat` |
| **화면 전환 후 상태** | 이동하면 초기화되는 결함 | `test_cart_kept_after_navigation` |
| **이탈 후 재진입** | 세션이 끊겼는데 화면이 남는 결함 | `test_logout_then_back_button` |
| **표시가 아닌 값** | 화면상 선택만 바뀌고 결과는 그대로인 결함 | `test_sort` |

특히 마지막이 중요합니다. 정렬 테스트에서 "정렬 옵션이 선택되었는지"를 확인하면
**정렬이 전혀 동작하지 않아도 통과**합니다. 그래서 실제 가격·이름 값의 순서를 비교합니다.

차단 케이스도 마찬가지입니다. "들어가지지 않았다"만 보면
**사유가 뒤바뀌어도 통과**하므로 안내 문구까지 확인합니다.

## 4. 의도적으로 제외한 것

빠뜨린 것이 아니라 **판단해서 뺀 것**입니다.

| 제외 | 이유 |
|---|---|
| 성능 문제 계정(`performance_glitch_user`) | 응답이 느린 계정. 자동화의 대기 시간 설계와 얽혀 실패 원인이 흐려집니다. 성능은 별도 계층에서 볼 문제입니다 |
| 이미지 깨짐 계정(`problem_user`) | 화면 표시 결함으로, 값 비교로는 잡히지 않습니다. 이미지 비교 도구가 필요한 영역입니다 |
| 반응형·모바일 해상도 | 데스크톱만 대상으로 한정했습니다. 넓히려면 해상도별 기대값을 따로 정의해야 합니다 |
| Firefox·Safari | 엔진이 달라 별도 확인이 필요합니다. 현재는 같은 엔진을 쓰는 Chrome·Edge 만 검증합니다 |
| 접근성 | 전용 도구가 필요하며 UI 자동화와 목적이 다릅니다 |

## 5. 실행 전략

| 구분 | 대상 | 소요 | 언제 |
|---|---|---|---|
| **smoke** | 4건 (기능별 핵심 흐름 1건씩) | 약 20초 | 코드가 올라올 때마다, 전체 실행 전 |
| **regression** | 24건 전체 | 병렬 실행 | smoke 통과 후 |

브라우저는 **Chrome(Linux)** 과 **Edge(Windows)** 두 조합을 함께 돌립니다.
한쪽이 실패해도 다른 쪽을 끝까지 실행해, 브라우저 문제인지 운영체제 문제인지를
한 번의 실행으로 구분합니다.

**smoke 를 먼저 두는 이유** — 핵심 흐름이 깨진 빌드는 전체를 돌릴 이유가 없습니다.
20초 만에 걸러내면 잘못된 빌드에 몇 분을 쓰지 않습니다.

**정기 실행** — 코드가 그대로여도 대상 사이트가 바뀌면 깨집니다.
변경이 없는 날에도 하루 한 번 돌려서, 문제를 다음 배포 때가 아니라 그날 알도록 했습니다.

## 6. 안정성 정책

간헐적으로 실패하는 테스트는 **결과를 믿을 수 없게 만들어 자동화 전체를 무력화**합니다.
"가끔 실패하니 다시 돌려보자"가 굳어지면 진짜 결함도 그렇게 넘어갑니다.

그래서 다음을 원칙으로 뒀습니다.

**1. 실패한 테스트를 조건 없이 재실행하지 않는다**

재실행으로 통과시키면 불안정한 원인이 그대로 남습니다.
이 저장소에는 재실행 옵션(`--reruns`)을 넣지 않았습니다.

**2. 재시도는 동작 단위로만, 확인 조건과 함께 한다**

`click()` 과 `send_keys()` 는 재시도하지만, **기대한 변화가 나타났는지 확인한 뒤**
반영되지 않았을 때만 다시 시도합니다. 결과를 확인하지 않는 재시도는
실패를 감출 뿐이라 두지 않았습니다.

**3. 대기는 시간이 아니라 조건으로 건다**

`time.sleep()` 을 쓰지 않습니다. 고정 대기는 느린 환경에서는 부족하고
빠른 환경에서는 낭비이며, 무엇을 기다리는지가 코드에 남지 않습니다.

**4. 실패한 순간의 화면을 남긴다**

다른 환경에서만 재현되는 실패는 로그만으로 좁히기 어렵습니다.
실패 시 화면과 HTML 을 파일로 남기고, CI 에서는 내려받을 수 있게 했습니다.

이 정책은 실제로 필요해서 만든 것입니다.
로컬에서 통과하던 테스트가 CI 에서 11건 깨졌고,
원인을 좁히는 과정은 [README](../README.md#안정성--간헐적-실패를-잡은-과정) 에 정리했습니다.

## 7. 알려진 한계

포트폴리오용으로 만든 것이라 실제 운영 스위트와 다음이 다릅니다.
**덮지 못한 부분을 아는 것도 설계의 일부**라 그대로 적습니다.

| 한계 | 실제 운영이라면 |
|---|---|
| 같은 엔진 브라우저 2종만 검증 | Firefox·Safari 등 다른 엔진과 버전 조합까지 매트릭스로 구성 |
| UI 계층만 검증 | API·데이터 계층에서 먼저 걸러 UI 케이스를 줄임 |
| 데모 사이트라 데이터 준비가 불필요 | 테스트 데이터 생성·정리를 fixture 로 관리 |
| 실패 알림 없음 | 실패 시 담당자에게 즉시 통지 |
| 24건 규모 | 케이스가 늘면 실행 시간 관리와 중복 제거가 별도 과제가 됨 |
